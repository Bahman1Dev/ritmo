# ADR 0006: Guard Rails and Dependency Rules

## Status
Accepted

## Context
As codebases grow, clean architectural boundaries tend to erode. Developers might accidentally import UI-layer controllers into domain engines, write raw SQL queries inside widgets, or couple feature modules together. Static lints in default Flutter projects are too relaxed to prevent these violations.

## Decision
We decided to enforce strict architectural guard rails and dependency boundaries:
1. **Linter Upgrade**: Adopt `package:very_good_analysis` for highly strict analysis rules.
2. **Layer Imports Restriction**:
   * **Domain Engines**: Must NOT import `package:flutter/*` or `dart:ui`. They must contain pure Dart code only.
   * **Presentation Layer**: Must NOT run direct SQL or database query helper methods. All data requests must pass through Repository interfaces.
   * **Cross-Feature Imports**: Features must communicate only via shared core events (`RitmoEventBus`) or interfaces.
3. **Decoupled Localization**: All user-facing strings generated by the backend (like strategy warning notices or system messages) must be retrieved dynamically via localizations (`AppLocalizations`) rather than being hardcoded in Persian strings in the domain layer.

## Consequences
### Positive
* Architecture integrity: Linter rules fail the CI build if boundaries are violated, ensuring long-term code quality.
* Decoupling: UI widgets can be modified without breaking background logic.
* High portability: Pure domain engines can be run in background isolates, CLI tools, or web-workers without GUI library overhead.

### Negative
* Strictness: Developers must write additional boilerplate code (like repository interfaces) instead of quick direct database queries.

## Alternatives Considered
* *Code Reviews only*: Relying on manual code reviews to enforce architecture. Rejected because manual reviews are error-prone and cannot systematically catch all import violations.
