### ۰.۱ باگ ۱ (بحرانی) — کانال آلارم در موتور پس‌زمینه وجود ندارد

هر چهار متد آلارم فقط داخل `MainActivity.configureFlutterEngine()` ثبت شده‌اند. اما وقتی کاربر روی دکمهٔ اعلان می‌زند و اپ بسته است، `NotificationActionReceiver` یک **موتور Flutter کاملاً جداگانه** می‌سازد و روی آن فقط `com.ritmo.app/notif_action_bg` را ثبت می‌کند.

```
کاربر «تعویق ⏰» را می‌زند (اپ بسته)
  → NotificationActionReceiver → FlutterEngine(appContext) جدید
  → NotificationActionDispatcher.handleAction('SNOOZE')
  → AlarmSchedulerService.snoozeReminder()
  → sl<AlarmPlatform>().cancelAlarm() / scheduleExactAlarm()
  → NativeBridge.invokeMethod روی کانال com.ritmo.app/alarms
  → 💥 MissingPluginException
  → در native_bridge.dart گرفته می‌شود، لاگ می‌شود، false برمی‌گرداند
  → هیچ‌کس false را چک نمی‌کند
```

نتیجه: دیتابیس می‌گوید `state='delayed'` و `snoozeUntil` ست شده، ولی **هیچ آلارمی در `AlarmManager` ثبت نشده**. آلارم قبلی هم یک‌بارمصرف بود و شلیک شده.

همین اتفاق برای موتور پس‌زمینهٔ `RitmoAgendaWidgetProvider` هم می‌افتد.

### ۰.۲ باگ ۲ (بحرانی) — تعویق برای همیشه گم می‌شود

در `scheduleNextAlarms()` شاخهٔ بازثبت این است:

```dart
if (remState == 'delayed' && snoozeTime != null && snoozeTime > nowMs) { ... }
continue;
```

چون آلارم هرگز ثبت نشده، کاربر اپ را دیرتر باز می‌کند و تا آن موقع `snoozeUntil` گذشته است. شرط رد می‌شود، `continue` می‌خورد و **آن یادآوری تا ابد در حالت `delayed` گیر می‌کند و دیگر هرگز زنگ نمی‌زند**. تعویق بی‌سروصدا تبدیل به حذف می‌شود.

### ۰.۳ باگ ۳ (بحرانی) — دو مسیر تعویق که وضعیت‌های متفاوت می‌نویسند

| ویژگی | مسیر اعلان | مسیر داخل اپ |
| --- | --- | --- |
| نقطهٔ ورود | `AlarmSchedulerService.snoozeReminder` | `RoutineActions.snoozeRoutine` → `SnoozeReminderHandler` |
| `routine_occurrences.status` | `'snoozed'` | `'rescheduled'` |
| `SnoozePolicy` اعمال می‌شود؟ | ❌ خیر | ✅ بله |
| آلارم native ثبت می‌شود؟ | ❌ خیر (باگ ۰.۱) | ✅ بله |

و `scheduleNextAlarms()` این کوئری را می‌زند:

```sql
WHERE (status = 'pending' OR status = 'snoozed') AND (date = ? OR date = ?)
```

یعنی ردیف‌هایی که `'rescheduled'` هستند **اصلاً توسط جاروی زمان‌بندی دیده نمی‌شوند**. دو مسیر دقیقاً مکمل هم خراب‌اند: مسیر اعلان وضعیت درست می‌نویسد ولی آلارم ثبت نمی‌کند؛ مسیر داخل اپ آلارم ثبت می‌کند ولی وضعیتی می‌نویسد که جارو نادیده می‌گیرد.

پیامد امنیتی: چون `SnoozePolicy` روی مسیر اعلان اجرا نمی‌شود، **از روی اعلان می‌شود یادآور دارو را بی‌نهایت بار عقب انداخت** و از `blockedMedical` و `blockedMidnight` و سقف `deferCount` رد شد.

### ۰.۴ باگ ۴ — `isRoutineZoneActive` کد مرده است

```kotlin
val dbPath = context.getDatabasePath("ritmo_secure.db")
if (!dbPath.exists()) return true
```

ولی `LegacyDatabaseRecovery.getSafeDatabasePath()` در اولین اجرا فایل `ritmo_secure.db` را به `ritmo.db` **rename** می‌کند. پس آن فایل هرگز وجود ندارد و این تابع همیشه فوراً `true` برمی‌گرداند.

یعنی قابلیت «یادآور را بیرون از زون خودش نشان نده» **هیچ‌وقت کار نکرده**.

<aside>
⚠️

**مین زیر پا:** اگر کسی صرفاً اسم فایل را به `ritmo.db` عوض کند، یک قابلیتِ خوابیده که *اعلان‌ها را سرکوب می‌کند* ناگهان فعال می‌شود — همراه با SQLite روی ترد اصلیِ `onReceive` (خطر ANR) و خواندن cross-process یک دیتابیس WAL. **اسم فایل را سرسری عوض نکن.** تصمیم قطعی در تسک T-A5.

</aside>

### ۰.۵ باگ ۵ — مهم‌ترین اعلان اپ به انگلیسی است

کل `res/values/strings.xml` انگلیسی است و هیچ `values-fa/` وجود ندارد:

```xml

<string name="notif_essential_channel_name">Vital Reminders (Medication/Prayer)</string>
<string name="notif_action_done">Done ✅</string>
```

در مقابل، مسیر غیرحیاتی رشته‌های فارسی را **hardcode** کرده («🌿 روتین روزانه»، «انجام شد ✅»، «تعویق ⏰»، «رد کردن»).

نتیجهٔ عملی: در یک اپ کاملاً فارسی و RTL، **اعلان کم‌اهمیت فارسی است و اعلان دارو انگلیسی**. اسم کانال‌ها هم در تنظیمات اندروید انگلیسی دیده می‌شود.

## ۱. قانون طلایی

<aside>
🚫

**«انجام شد» فقط وقتی معنا دارد که هر سه شرط برقرار باشد:** ۱) کد نوشته شده و کامپایل می‌شود. ۲) یک **مسیر فراخوانی واقعی** از UI یا از یک broadcast واقعی به آن می‌رسد (با `rg` ثابتش کن). ۳) سناریوی پذیرش روی **دستگاه واقعی یا امولاتور** اجرا شده و خروجی مشاهده شده است. فایل یتیم = انجام‌نشده — دقیقاً همان اشتباهی که در پرامپت ۰۵۹ رخ داد.

</aside>

قواعد مکمل:

- **هیچ تسکی را رد نکن.** اگر تسکی را نمی‌توانی انجام دهی، در گزارش با دلیل فنی بنویس «انجام نشد».
- **هیچ فایل جدیدی نساز مگر در فهرست تسک صریحاً آمده باشد.**
- بعد از هر فاز `flutter analyze` بزن و باید صفر خطا بدهد (`very_good_analysis` فعال است).
- رشته‌های فارسی را از `strings.xml` بخوان، نه hardcode در Kotlin.

## ۳. تصمیم‌های قطعی محصولی (بحث نکن، اجرا کن)

1. **دامنهٔ تمام‌صفحه:** پیش‌فرض فقط `isEssential = 1` و آیتم‌های دارویی. علاوه بر آن یک ستون `routines.fullScreenAlarm` اضافه می‌شود تا کاربر بتواند برای هر روتین دلخواه هم روشنش کند. یک کلید سراسری `notif_fullscreen_enabled` هم بالای همه است.
2. **اگر مجوز تمام‌صفحه رد شد**، معماری باید بی‌سروصدا به heads-up با `CATEGORY_ALARM` سقوط کند. هرگز crash نکن، هرگز اعلان را حذف نکن.
3. **`isRoutineZoneActive` حذف می‌شود**، نه تعمیر. دلیل در T-A5.
4. **وضعیت واحد تعویق `'snoozed'` است.** `'rescheduled'` حذف می‌شود.
5. **صدای آلارم**: از `RingtoneManager.TYPE_ALARM` با `AudioAttributes.USAGE_ALARM` فقط برای کانال حیاتی. کانال عادی صدای پیش‌فرض اعلان.

## ۴. فاز A — نجات (قبل از هر قابلیت جدید)

### T-A1 — ثبت کانال آلارم روی موتور پس‌زمینه

**فایل جدید:** `android/app/src/main/kotlin/ir/ritmo/app/AlarmChannelRegistrar.kt`

منطق ثبت کانال آلارم را از `MainActivity.configureFlutterEngine()` بیرون بکش و در یک object مشترک بگذار:

```kotlin
package ir.ritmo.app

import android.content.Context
import io.flutter.plugin.common.BinaryMessenger
import io.flutter.plugin.common.MethodChannel

object AlarmChannelRegistrar {
    fun register(context: Context, messenger: BinaryMessenger) {
        MethodChannel(messenger, NativeChannels.ALARMS).setMethodCallHandler { call, result ->
            when (call.method) {
                AlarmMethods.SCHEDULE_EXACT_ALARM -> { /* منطق فعلی MainActivity */ }
                AlarmMethods.CANCEL_ALARM -> { /* منطق فعلی MainActivity */ }
                AlarmMethods.CHECK_EXACT_ALARM_PERMISSION -> { /* ... */ }
                AlarmMethods.REQUEST_EXACT_ALARM_PERMISSION -> { /* ... */ }
                else -> result.notImplemented()
            }
        }
    }
}
```

<aside>
⚠️

منطق فعلی داخل `MainActivity` به `this` (اکتیویتی) وابسته است. همه را به `context: Context` تبدیل کن. برای `REQUEST_EXACT_ALARM_PERMISSION` که واقعاً به اکتیویتی نیاز دارد، در حالت پس‌زمینه `result.error("NO_ACTIVITY", ...)` برگردان — این متد از پس‌زمینه صدا زده نمی‌شود.

</aside>

**ویرایش ۱ —** `MainActivity.kt`: بلوک کانال آلارم را حذف کن و جایش بگذار:

```kotlin
AlarmChannelRegistrar.register(applicationContext, flutterEngine.dartExecutor.binaryMessenger)
```

**ویرایش ۲ —** `NotificationActionReceiver.kt`: بلافاصله بعد از ساخت موتور و قبل از `sMethodChannel = ...`:

```kotlin
sBackgroundEngine = engine
AlarmChannelRegistrar.register(appContext, engine.dartExecutor.binaryMessenger)
sMethodChannel = MethodChannel(engine.dartExecutor.binaryMessenger, "com.ritmo.app/notif_action_bg")
```

**ویرایش ۳ —** همین کار را در موتور پس‌زمینهٔ `RitmoAgendaWidgetProvider.kt` انجام بده.

**سند پذیرش:** با اپ بسته (force stop شده) روی «تعویق ⏰» بزن. در logcat نباید هیچ `MissingPluginException` ببینی و باید ثبت آلارم جدید را ببینی.

### T-A2 — شکست native را بلند کن، نه بی‌صدا

**فایل:** `lib/core/services/native_bridge.dart`

همین که `MissingPluginException` گرفته می‌شد و `false` برمی‌گشت، باعث شد این باگ ماه‌ها پنهان بماند.

1. در `scheduleExactAlarm` و `cancelAlarm`، بعد از `RitmoLog.error` یک شمارنده در `app_settings` بالا ببر: کلید `alarm_native_failure_count`.
2. مقدار بازگشتی را همه‌جا **چک کن**. در `snooze_reminder_handler.dart` و `alarm_scheduler_service.dart`:

```dart
final ok = await sl<AlarmPlatform>().scheduleExactAlarm(
  id: reminderId, timeMsUTC: snoozeUntilMs, title: title, isEssential: isEssential,
);
await db.update(
  'pending_reminders',
  {'nativeScheduled': ok ? 1 : 0},
  where: 'id = ?', whereArgs: [reminderId],
);
if (!ok) {
  RitmoLog.error('ALARM', 'Native alarm registration FAILED for $reminderId');
}
```

ستون `nativeScheduled` در مهاجرت T-A4 ساخته می‌شود. این ستون شکست نامرئی را به یک **واقعیت قابل کوئری در دیتابیس** تبدیل می‌کند و پایهٔ دیدبان فاز D است.

### T-A3 — یکی‌کردن مسیر تعویق

**فایل:** `lib/core/services/notification_action_dispatcher.dart`

در `case 'SNOOZE':` فراخوانی مستقیم `AlarmSchedulerService.snoozeReminder` را **حذف** کن و جایش بگذار:

```dart
case 'SNOOZE':
  final verdict = await SnoozePolicy.evaluate(
    itemId: routineId,
    domain: 'routine',
    dateStr: dateStr,
  );
  switch (verdict.verdict) {
    case SnoozeVerdict.allowed:
    case SnoozeVerdict.lastCall:
      await RitmoExecutionKernel.instance.execute(
        SnoozeReminderCommand(
          reminderId: reminderId,
          snoozeMinutes: verdict.allowedMinutes,
          dateStr: dateStr,
        ),
      );
    case SnoozeVerdict.exhausted:
    case SnoozeVerdict.blockedMedical:
    case SnoozeVerdict.blockedMidnight:
      await _postBlockedSnoozeNotification(reminderId, verdict);
  }
```

`_postBlockedSnoozeNotification` باید اعلان را دوباره پست کند با متن `verdict.userMessage` و اکشن‌های خروج از `verdict.exits` — نه اینکه بی‌سروصدا هیچ کاری نکند. کاربر باید بفهمد چرا تعویقش کار نکرد.

**سپس:** متد `AlarmSchedulerService.snoozeReminder` را حذف کن. اگر `rg -n "snoozeReminder" lib/` بعد از این کار چیزی جز تعریف خودش برگرداند، کار تمام نشده.

### T-A4 — مهاجرت V73 و یکسان‌سازی وضعیت

**فایل جدید:** `lib/core/database/migration/migrations/migration_v73_notification_reliability.dart`

```dart
class MigrationV73NotificationReliability implements Migration {
  @override
  int get version => 73;

  @override
  Future<void> up(Database db) async {
    // ۱. ستون ردیابی موفقیت ثبت آلارم native
    await safeAddColumn(db, 'pending_reminders', 'nativeScheduled', 'INTEGER DEFAULT 0');

    // ۲. انتخاب کاربر برای اعلان تمام‌صفحه در سطح روتین
    await safeAddColumn(db, 'routines', 'fullScreenAlarm', 'INTEGER DEFAULT 0');

    // ۳. یکسان‌سازی وضعیت تعویق
    await db.rawUpdate(
      "UPDATE routine_occurrences SET status = 'snoozed' WHERE status = 'rescheduled'",
    );

    // ۴. دفتر تحویل آلارم برای دیدبان قابلیت‌اطمینان
    await db.execute('''
      CREATE TABLE IF NOT EXISTS alarm_delivery_log (
        id TEXT PRIMARY KEY,
        reminderId TEXT NOT NULL,
        routineId TEXT,
        expectedAt INTEGER NOT NULL,
        firedAt INTEGER,
        outcome TEXT NOT NULL,
        createdAt INTEGER NOT NULL
      )
    ''');
    await db.execute(
      'CREATE INDEX IF NOT EXISTS idx_alarm_delivery_expected ON alarm_delivery_log(expectedAt)',
    );
  }
}
```

`outcome` ∈ `scheduled` / `fired` / `missed` / `native_failed`.

**ویرایش‌های الزامی بعد از مهاجرت:**

1. `database_helper.dart`: `_dbVersion = 73`.
2. `migration_runner.dart`: `MigrationV73NotificationReliability()` را به انتهای `_migrations` اضافه کن.
3. `snooze_reminder_handler.dart`: در `rawUpdate` مقدار `'rescheduled'` را به `'snoozed'` تغییر بده — **در هر دو جا** (هم `UPDATE` و هم `insert` وقتی `affected == 0`).
4. `rg -n "rescheduled" lib/` باید بعد از این کار خالی باشد.

### T-A5 — حذف `isRoutineZoneActive`

**فایل:** `BootReceiver.kt`

تابع `isRoutineZoneActive` و همهٔ فراخوانی‌هایش را حذف کن. همچنین `import android.database.sqlite.SQLiteDatabase` را بردار.

### T-B4 — مجوز و تنظیمات

`shouldUseFullScreen` باید **هر چهار شرط** را چک کند:

```kotlin
private fun shouldUseFullScreen(context: Context, id: String, isEssential: Boolean): Boolean {
    val prefs = context.getSharedPreferences("FlutterSharedPreferences", Context.MODE_PRIVATE)
    // ۱. کلید سراسری
    if (prefs.getString("flutter.notif_fullscreen_enabled", "true") != "true") return false
    // ۲. دامنه: حیاتی یا انتخاب کاربر برای همین روتین
    val scope = prefs.getString("flutter.notif_fullscreen_scope", "essential")
    val optedIn = prefs.getStringSet("flutter.notif_fullscreen_ids", emptySet())?.contains(id) == true
    if (scope == "essential" && !isEssential && !optedIn) return false
    // ۳. مجوز اندروید ۱۴+
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
        val nm = context.getSystemService(NotificationManager::class.java)
        if (!nm.canUseFullScreenIntent()) return false
    }
    return true
}
```

<aside>
🚨

**نکتهٔ حیاتی برای انتشار:** از اندروید ۱۴ (API 34) به بعد `USE_FULL_SCREEN_INTENT` دیگر خودکار اعطا نمی‌شود. فقط اپ‌های تقویم و ساعت زنگ‌دار پیش‌فرض آن را می‌گیرند. بقیه باید کاربر را با `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` به تنظیمات بفرستند. معماری باید از روز اول فرض کند این مجوز **ممکن است رد شود** و بی‌سروصدا به heads-up با `CATEGORY_ALARM` سقوط کند. برای بازار و مایکت مسئلهٔ بازبینی نیست، ولی رفتار دستگاه یکسان است.

</aside>

**تنظیمات در `lib/features/profile/presentation/profile_screen.dart`** — بخش جدید «اعلان‌ها و آلارم»:

| کلید `app_settings` | نوع | پیش‌فرض | برچسب فارسی |
| --- | --- | --- | --- |
| `notif_fullscreen_enabled` | bool | `'true'` | «اعلان تمام‌صفحه برای یادآورهای مهم» |
| `notif_fullscreen_scope` | `essential`/`all` | `'essential'` | «دامنهٔ اعلان تمام‌صفحه» |
| `notif_alarm_sound_enabled` | bool | `'true'` | «پخش با صدای آلارم به‌جای صدای اعلان» |

همهٔ این کلیدها باید بعد از تغییر، `SnapshotSyncService.syncAll()` را صدا بزنند تا در `SharedPreferences` منعکس شوند. **این را فراموش نکن** — وگرنه Kotlin هرگز تغییر را نمی‌بیند. همچنین `SnapshotHelper.updateNotificationSettingsSnapshot` را طوری گسترش بده که این سه کلید را هم بنویسد.

```kotlin
    .setChoices(arrayOf("خسته بودم", "وقت نشد", "حسش نبود", "یادم رفت"))
    .build()
```

مقدار دریافتی را در `NotificationActionReceiver` بخوان و به `SkipOccurrenceCommand(reason: …)` پاس بده. این مستقیماً جدول `skip_reasons` را پر می‌کند که موتورهای پرامپت ۰۵۹ به آن نیاز دارند و امروز خالی است.

<aside>
💡

**تعویق را از «تأخیر» به «تصمیم» تبدیل کن.** وقتی `SnoozePolicy` مقدار `lastCall` برگرداند، متن دکمه را به‌جای «تعویق ⏰» بگذار «۲ دقیقه‌اش را همین الان؟» و آن را به `minimalDurationMinutes` وصل کن. منطقش در `SnoozePolicy` هست؛ فقط مسیر اعلان تا امروز از آن رد نمی‌شد.

</aside>

## ۷. فاز D — دیدبان قابلیت‌اطمینان

### T-D1 — صفحهٔ تشخیص

**فایل جدید:** `lib/features/profile/presentation/notification_diagnostics_screen.dart`

از `profile_screen.dart` با ردیف «بررسی سلامت اعلان‌ها» بازش کن. باید نشان دهد:

| بخش | منبع |
| --- | --- |
| مجوز اعلان | `POST_NOTIFICATIONS` |
| مجوز آلارم دقیق | `AlarmMethods.CHECK_EXACT_ALARM_PERMISSION` |
| مجوز تمام‌صفحه | `canUseFullScreenIntent()` |
| بهینه‌سازی باتری | `isIgnoringBatteryOptimizations` |
| دسترسی DND | `isNotificationPolicyAccessGranted` |
| وضعیت کانال‌ها | `importance` واقعی هر کانال از `NotificationManager` |
| ۲۰ رویداد آخر | `notification_history` |
| آلارم‌های ازدست‌رفته | `alarm_delivery_log WHERE outcome='missed'` |
| شکست‌های native | `pending_reminders WHERE nativeScheduled = 0` |

و یک دکمه: **«ارسال آلارم آزمایشی تا ۱۵ ثانیهٔ دیگر»** که یک `pending_reminders` موقت با `isEssential=1` می‌سازد و مسیر کامل را می‌زند. این دکمه تنها راهی است که کاربر می‌تواند بفهمد اعلان روی گوشی خودش کار می‌کند یا نه.

برای هر مورد قرمز، یک دکمهٔ «درستش کن» که مستقیم به Intent تنظیمات مربوطه می‌رود.

### T-D2 — دیدبان پس‌زمینه

**فایل جدید:** `lib/core/services/notification_watchdog_service.dart`

یک تسک `workmanager` روزانه که `sweepMissedAlarms()` را اجرا کند و اگر در ۷ روز گذشته بیش از سه آلارم ازدست‌رفته بود، یک آیتم در `CentralInboxService` بگذارد:

> «۳ یادآوری در روزهای اخیر به دست شما نرسید. احتمالاً بهینه‌سازی باتری جلوی ریتمو را گرفته است.»
> 

با لینک مستقیم به صفحهٔ تشخیص.

<aside>
🇮🇷

با توجه به سهم بالای شیائومی و سامسونگ در ایران و کشتار پس‌زمینهٔ تهاجمی MIUI، این تنها راه فهمیدن این است که اپ روی گوشی واقعی کاربر کار می‌کند یا نه. بدون این، هر گزارش «اعلان نیامد» غیرقابل تشخیص می‌ماند.

</aside>

## ۹. قواعد سخت

1. **هیچ رشتهٔ فارسی hardcode در Kotlin.** همه از `strings.xml`.
2. **هیچ SQLite در Kotlin.** بعد از T-A5 هیچ `SQLiteDatabase` در `android/` نباید بماند. با `rg -n "SQLiteDatabase" android/` تأیید کن.
3. **هیچ کار مسدودکننده در `onReceive`.** اگر لازم شد از `goAsync()` استفاده کن.
4. **هیچ wake lock بدون timeout.**
5. **هیچ اکشن چهارم.**
6. `PendingIntent` همیشه با `FLAG_IMMUTABLE`.
7. مقدار بازگشتی `AlarmPlatform` هرگز نادیده گرفته نشود.
8. **هیچ ستون یا جدولی خارج از مهاجرت V73 اضافه نشود.**
9. هر رفتار جدیدِ مزاحم (تمام‌صفحه، bypass DND، wake lock) باید **کلید خاموشی** داشته باشد.
10. اگر مجوزی رد شد، سقوط نرم — نه crash، نه اعلان ازدست‌رفته.
