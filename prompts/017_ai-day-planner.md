# 017 — برنامه‌ریز روز با AI (AI Day Planner / «روزم رو بچین»)

**نقش تو:** ایجنت کدنویس ارشد Flutter/Dart. این سند را کامل بخوان و دقیقاً اجرا کن.
**قانون طلایی:** قبل از هر Stage وضعیت فعلی کد را بررسی کن و فقط چیزی را بساز که وجود ندارد.

## ⛔ قواعد اجرا — قبل از هر کاری بخوان و تخطی نکن

1. **همین سند، Implementation Plan است.** برنامه اجرایی جدید نساز، roadmap ننویس، فاز‌بندی خودت را اختراع نکن، و هیچ فایل plan/todo/design جدیدی ایجاد نکن. تنها فایل مستندی که می‌سازی `prompts/017_REPORT.md` در پایان کار است.
2. **مستقیم برو سراغ کد.** خروجی تو کد است، نه متن. اگر عادت داری قبل از کد یک Implementation Plan تولید کنی، این‌جا ممنوع است — Stage A را باز کن و اولین فایل را بساز.
3. **ترتیب Stageها را دقیقاً رعایت کن:** A → B → C → D → E → F. هیچ Stage را جلو نینداز، ادغام نکن، و حذف نکن.
4. **در ابهام، طراحی نکن — تصمیم کوچک بگیر.** اگر جزئی در سند مشخص نشده (نام فایل، متن یک label و…)، کوچک‌ترین تصمیم سازگار با معماری موجود را بگیر، ادامه بده، و یک خط در REPORT ثبت کن. برای ابهام‌ها سؤال‌نامه یا سند تحلیل تولید نکن.
5. **خارج از این سند هیچ چیزی را تغییر نده:** نه refactor، نه rename، نه «بهبود» فایل‌های موجود، مگر جایی که خود سند صریحاً خواسته.
6. هر جا این سند با برداشت/سلیقه تو تعارض داشت، **سند برنده است.**

## ۱. هدف

کاربر روزش را به زبان طبیعی فارسی تعریف می‌کند — مثل حرف زدن با یک مدیر برنامه انسانی:

> «فردا صبح ۵ بیدار می‌شم، دعا می‌خونم، نماز می‌خونم، بعد صبحونه می‌خورم، بعد می‌رم بانک، بعد می‌رم سرکار و تا ۱ اونجام…»

و دستیار AI باید:

1. کل روایت را به یک **برنامه ساخت‌یافته روز** تبدیل کند (آیتم‌ها با زمان شروع، مدت، دسته‌بندی، ماژول مقصد).
2. مدت کارهایی که گفته نشده را **حدس بزند** (با منطق چندلایه — بخش ۴) یا اگر ابهام پرهزینه است **بپرسد** (حداکثر ۳ سؤال — بخش ۵).
3. **پیشنهاد بهبود** بدهد: بافر رفت‌وآمد، لنگر به وقت شرعی، زنجیره خواب، هشدار تداخل.
4. برنامه نهایی را در یک **پیش‌نمایش تایم‌لاین قابل‌ویرایش** نشان دهد و فقط بعد از تأیید کاربر، **به‌صورت دسته‌ای و اتمیک** در بخش‌های مربوطه برنامه (روتین‌ها، تسک‌های یک‌بارمصرف، عبادات، خواب) ثبت کند.
5. کل عملیات **قابل Undo** باشد.

این قابلیت روی زیرساخت موجود سوار می‌شود؛ **هیچ زیرساخت موازی نساز**.

## ۳. Stage A — قرارداد JSON و مدل Draft

یک سرویس جدید `DayPlanComposer` بساز (پیشنهاد: `lib/features/assistant/logic/day_plan_composer.dart`) که با system prompt اختصاصی، `ai_gateway` را صدا می‌زند و **فقط JSON خالص** برمی‌گرداند (بدون متن آزاد؛ اگر مدل متن اضافه داد، JSON را با همان الگوی مقاوم `ChatActionParser` استخراج کن).

قرارداد خروجی LLM (نمونه — نام‌گذاری نهایی با تو):

```json
{
  "planDate": "2026-07-16",
  "items": [
    {
      "title": "بیدار شدن",
      "targetModule": "sleep",          // sleep | worship | routine | task | event | reminder
      "start": {"kind": "clock", "time": "05:00"},
      "durationMin": null,
      "durationSource": "none",
      "recurrence": "oneOff",            // oneOff | daily | daysOfWeek
      "daysOfWeek": null,
      "category": "personal",           // از enum دسته‌های موجود
      "confidence": 0.95,
      "note": null
    },
    {
      "title": "نماز صبح",
      "targetModule": "worship",
      "start": {"kind": "anchor", "anchorEvent": "FAJR", "offsetMin": 10},
      "durationMin": 15,
      "durationSource": "estimated"
    },
    {
      "title": "بانک",
      "targetModule": "task",
      "start": {"kind": "after_previous", "bufferMin": 20},
      "durationMin": 45,
      "durationSource": "estimated",
      "note": "بافر ۲۰ دقیقه رفت‌وآمد اضافه شد"
    }
  ],
  "questions": [
    {"id": "q1", "itemRef": 4, "text": "رفت‌وآمد از بانک تا سرکار چقدر طول می‌کشد؟", "quickReplies": ["۱۵ دقیقه", "۳۰ دقیقه", "۴۵ دقیقه"]}
  ],
  "suggestions": [
    {"text": "برای بیداری ساعت ۵، بهتر است امشب قبل از ۲۲:۳۰ بخوابی.", "action": "setBedtime", "payload": {"time": "22:30"}}
  ]
}
```

نکات قرارداد:
- `start.kind` سه حالت دارد: `clock` (ساعت صریح)، `anchor` (وقت شرعی — برای عبادات **همیشه** لنگر شرعی به‌جای ساعت ثابت، چون اذان هر روز جابه‌جا می‌شود)، `after_previous` (زنجیره‌ای نسبت به آیتم قبل + بافر).
- «فردا می‌رم بانک» ⇒ `recurrence: oneOff` ⇒ ثبت به‌صورت `itemType='TASK'` با `startDate` مشخص. «هر روز نماز می‌خونم» ⇒ روتین تکرارشونده. تشخیص این تمایز وظیفه LLM است و در system prompt با مثال فارسی توضیح بده.
- سمت Dart یک مدل `DayPlanDraft`/`DayPlanItemDraft` تایپ‌شده بساز با اعتبارسنجی سخت‌گیرانه (JSON نامعتبر ⇒ یک retry با پیام خطای ساخت‌یافته به مدل؛ باز هم شکست ⇒ پیام خطای انسانی، نه کرش).

## ۴. Stage B — موتور تخمین مدت (DurationEstimator)

سرویس محلی مستقل از LLM. برای هر آیتمی که `durationMin` ندارد، به این ترتیب اولویت:

1. **گفته صریح کاربر** («تا ۱ اونجام» ⇒ پایان صریح؛ مدت = پایان − شروع).
2. **تاریخچه خود کاربر:** میانه `durationMinutes` از `routine_completions` برای روتین‌هایی با عنوان/دسته مشابه (تطبیق ساده متنی + category کافی است؛ embedding نساز).
3. **حافظه AI (سند ۰۱۶):** فکت‌هایی مثل «رفت‌وآمد تا محل کار ۳۰ دقیقه است».
4. **جدول پیش‌فرض‌های زندگی ایرانی** (ثابت در کد، قابل‌ترجمه به تنظیمات بعداً): نماز ۱۰–۱۵، دعا/قرآن ۱۵، صبحانه ۲۰، ناهار ۳۰، کار بانکی ۴۵، دوش ۲۰، رفت‌وآمد شهری پیش‌فرض ۳۰، خرید ۴۰ و… (جدول را خودت کامل کن، حدود ۲۰–۳۰ ردیف).
5. **حدس LLM** (همان `durationMin` که مدل داده) به‌عنوان آخرین راه.

خروجی هر تخمین باید `durationSource` (`user | history | memory | default | llm`) داشته باشد و در UI پیش‌نمایش، مدت‌های حدسی با نشان «حدسی» متمایز شوند.

## ۵. Stage C — حلقه شفاف‌سازی (پرسیدن به‌جای حدس کور)

- سیاست: **حدس بزن مگر اینکه ابهام پرهزینه باشد.** پرهزینه یعنی: زمان شروع/پایان کل بازه‌های بزرگ روز نامعلوم، تداخل جدی، یا آیتمی که بدون جواب اصلاً قابل ثبت نیست.
- حداکثر **یک راند** سؤال با حداکثر **۳ سؤال**؛ هر سؤال با quickReply چیپ در UI. جواب‌ندادن ⇒ بهترین حدس + نشان «حدسی».
- جواب‌های کاربر به سؤال‌های تکرارشونده (مثل مدت رفت‌وآمد) را با `memoryOps` در حافظه ذخیره کن تا دفعه بعد پرسیده نشود.

## ۶. Stage D — غنی‌سازی و اعتبارسنجی محلی (deterministic، بدون LLM)

بعد از دریافت draft و قبل از پیش‌نمایش، یک `DayPlanValidator` محلی:

1. **حل زنجیره زمان:** آیتم‌های `after_previous` را به ساعت مطلق تبدیل کن؛ لنگرهای شرعی را با سرویس اوقات شرعی موجود resolve کن.
2. **تداخل با برنامه موجود:** برنامه همان روز را از `day_agenda_service` بگیر و همپوشانی‌ها را علامت بزن (سطح آیتم: badge «تداخل با …» + پیشنهاد جابه‌جایی؛ auto-resolve نکن).
3. **بافر جابه‌جایی:** بین دو آیتم بیرون از خانه در دو مکان متفاوت، اگر بافر نیست اضافه کن (از حافظه/پیش‌فرض).
4. **زنجیره خواب:** اگر بیداری زودتر از الگوی فعلی است، پیشنهاد bedtime بده (از `SleepTarget` موجود).
5. **سلامت کل روز:** مجموع مدت‌ها + بافرها نباید از بازه بیداری بیشتر شود؛ اگر شد، هشدار «روزت جا نمی‌شود، این‌ها را کوتاه/حذف کن» با پیشنهاد مشخص.

## ۷. Stage E — پیش‌نمایش، Commit اتمیک، Undo

1. **شیت پیش‌نمایش تایم‌لاین:** نمای عمودی کل روز (الهام از Journey timeline موجود). هر آیتم: عنوان، بازه زمانی، badge ماژول مقصد (روتین/تسک/عبادت/خواب)، badge «حدسی» یا «تداخل». قابلیت‌های ویرایش قبل از تأیید: تغییر ساعت و مدت، حذف آیتم، سوییچ یک‌بارمصرف↔تکرارشونده، ویرایش عنوان. از الگوی `assistant_action_preview_sheet` موجود پیروی کن ولی این شیت مخصوص و تمام‌صفحه است.
2. **اکشن دسته‌ای جدید:** `AssistantActionType.applyDayPlan` به enum و registry اضافه کن. اجرای آن = حلقه روی آیتم‌های تأییدشده و فراخوانی **همان executorهای موجود** (`createRoutine` با `itemType` مناسب، `createWorshipItem`، تنظیم خواب و…). داخل **یک تراکنش دیتابیس**؛ شکست وسط کار ⇒ rollback کامل.
3. **Undo:** شناسه همه رکوردهای ساخته‌شده را در یک رکورد `day_plan_commits` (جدول کوچک جدید یا `system_tables`) نگه دار. بعد از commit، اسنک‌بار «برنامه ثبت شد — بازگردانی» + دکمه بازگردانی در صفحه دستیار تا ۲۴ ساعت. بازگردانی = حذف/آرشیو همان رکوردها.

## ۸. Stage F — نقاط ورود و حلقه یادگیری

1. **نقاط ورود:** کارت/CTA «روزم رو بچین» در صفحه دستیار (`assistant_screen.dart`) + وقتی کاربر در چت اصلی روایت چندکاره‌ای می‌نویسد، `ChatActionParser`/روتر چت به این فلو هدایت کند (تشخیص: بیش از ~۳ فعل برنامه‌ریزی در یک پیام).
2. **حلقه یادگیری تخمین:** در پایان روز (یا دفعه بعدِ باز شدن برنامه)، مدت واقعی ثبت‌شده را با تخمین مقایسه کن و اگر اختلاف معنادار تکرار شد، فکت اصلاحی در `ai_memory` بنویس («کار بانکی‌اش معمولاً ~۹۰ دقیقه طول می‌کشد»). UI اضافه نمی‌خواهد؛ فقط دادهٔ بهتر برای دفعات بعد.
3. **l10n:** همه رشته‌های جدید در فایل‌های arb.

## ۹. سناریوی پذیرش (Acceptance)

ورودی کاربر (باید end-to-end کار کند):

> «فردا صبح ساعت ۵ بیدار می‌شم، دعا می‌خونم، نماز می‌خونم، بعد صبحونه می‌خورم، بعد می‌رم بانک، بعد می‌رم سرکار و تا ۱ اونجام»

انتظار:
- بیداری ۵:۰۰ (پیشنهاد bedtime امشب)، دعا ~۱۵ دقیقه، نماز صبح **با لنگر اذان صبح** نه ساعت ثابت، صبحانه ~۲۰ دقیقه، بافر رفت‌وآمد قبل از بانک، بانک ~۴۵ دقیقه، بافر تا محل کار (اگر در حافظه نیست ⇒ جزو حداکثر ۳ سؤال)، کار با **پایان صریح ۱۳:۰۰**.
- همه به‌صورت `oneOff/TASK` برای فردا ثبت شوند مگر کاربر در پیش‌نمایش تکرارشونده‌شان کند (نماز/دعا را با سوییچ ساده بتواند روتین روزانه کند).
- قبل از تأیید هیچ چیزی در DB نوشته نشود؛ بعد از تأیید همه آیتم‌ها در بخش‌های درست برنامه دیده شوند؛ Undo همه را برگرداند.
- `flutter analyze` بدون خطای جدید؛ تست واحد برای: پارس JSON نامعتبر، DurationEstimator (هر ۵ لایه)، حل زنجیره `after_previous`، تشخیص تداخل، rollback تراکنش.

## ۱۰. Out of Scope (وارد نشو)

- برنامه‌ریزی هفتگی/ماهانه (فعلاً فقط یک روز، حداکثر «امروز/فردا/پس‌فردا»).
- ورودی صوتی.
- جابه‌جایی خودکار برنامه وسط روز وقتی کاری عقب افتاد (auto-reschedule).
- قالب‌های روز ذخیره‌شده (Day Templates) — نسخه بعد.
- هر تغییری در فلوهای موجود `quick_add_parser` و شیت‌های دستیار حوزه‌ای.
- sync ابری.

## ۱۱. Definition of Done

1. سناریوی بخش ۹ روی دستگاه/emulator سبز است (اسکرین‌شات یا شرح گام‌به‌گام در گزارش).
2. اکشن `applyDayPlan` در registry با preview→confirm→undo کامل است و هیچ مسیر نوشتن مستقیم به DB خارج از executorهای موجود ساخته نشده.
3. Rule 0.5 رعایت شده (آیتم‌های private در کانتکست LLM نیستند) — در گزارش نشان بده کجا فیلتر می‌شود.
4. تست‌های بخش ۹ پاس؛ `flutter analyze` تمیز.
5. گزارش نهایی را در `prompts/017_REPORT.md` بنویس: چه ساختی، چه تصمیم‌هایی گرفتی، چه چیزی از قبل موجود بود و دوباره نساختی.
