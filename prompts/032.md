## بخش ۱ — سیاست تعویق

### T1 — **B1: `isEssential` و سقف پیکربندی‌شده پاس داده نمی‌شوند** 🔴

فراخوان فعلی در `action_router.dart`:
```

final decision = SnoozePolicy.evaluate(

itemId: [targetRoutine.id](http://targetRoutine.id),

now: [DateTime.now](http://DateTime.now)(),

requestedMinutes: requestedMinutes,

currentDeferCount: currentDeferCount,

category: [targetRoutine.category.name](http://targetRoutine.category.name),   // 🔴 isEssential و configuredMax غایب

);

```

`SnoozePolicy.maxCap` هر دو را می‌پذیرد و بر اساسشان سقف را به ۲ کاهش می‌دهد — **ولی هیچ‌وقت دریافتشان نمی‌کند.** نتیجه: روتین‌های حیاتی سقف ۳ می‌گیرند به‌جای ۲.

**رفع:**
```

isEssential: targetRoutine.isEssential ? 1 : 0,

configuredMax: await _configuredMaxDefer(),

recurrenceRuleType: <از زمان‌بندی روتین>,

```

یک هلپر جدید بساز که کلید `snooze_max_defer_count` را می‌خواند (پیش‌فرض `3`، مقادیر نامعتبر → `3`).

⚠️ `recurrenceRuleType` هم پاس داده نمی‌شود؛ در نتیجه `ExitOption.moveToTomorrow` **همیشه** نمایش داده می‌شود، حتی برای روتین روزانه که منطقاً نباید. از `routine_schedules.recurrenceRule` بخوان.

### T2 — **B2: `blockedMedical` کد مرده است** 🔴

`ActionRouter` برایش `case` دارد، اما `SnoozePolicy.evaluate` این حالت را **هرگز** برنمی‌گرداند. فقط `allowed`، `lastCall`، `exhausted`، `blockedMidnight`.

**تصمیم معماری — گزینهٔ الف را پیاده کن:**

> **الف)** رفتار فعلی درست است (دارو تعویق‌پذیر است ولی با سقف ۲). پس `SnoozeVerdict.blockedMedical` **از enum حذف شود** و `case` مربوطه از روتر پاک شود.

⛔ گزینهٔ ب (مسدود کردن کامل تعویق دارو) را پیاده نکن — با «حداقل یک‌بار تعویق برای دارو» که کاربر تأیید کرده در تضاد است.

**قانون کد مرده:** بعد از حذف، `rg -n "blockedMedical" lib/` باید **صفر نتیجه** بدهد.

### T3 — **B7: `lastCall` به‌عنوان خطا نمایش داده می‌شود** ⚠️

if (decision.verdict == SnoozeVerdict.lastCall && context.mounted) {

**رفع:** یک حالت سوم به `ActionFeedback` اضافه کن:

static void info(BuildContext context, {required String message});

با رنگ `colors.warning` و بدون هپتیک خطا. ⛔ کل کلاس را بازنویسی نکن — فقط یک متد اضافه کن.

## بخش ۲ — «به فردا منتقل کن» باید واقعاً منتقل کند

### T4 — **B3: پیام موفقیت دروغ است** 🔴

در `_showExitOptionsSheet`:
```

CompletionGateway.instance.submit(RoutineSkip(reason: 'موکول شد به فردا'))

→ ActionFeedback.success(message: 'روتین به فردا موکول شد')

```

اما `RoutineSkip` فقط `routine_occurrences.status = 'skipped'` می‌زند و **هیچ رخدادی برای فردا نمی‌سازد**. کاربر فکر می‌کند فردا آن را می‌بیند؛ نمی‌بیند.

**رفع — نوع درخواست جدید در `completion_request.dart`:**
```

final class RoutineReschedule extends CompletionRequest {

const RoutineReschedule({

required this.routineId,

required this.fromDateStr,

required this.toDateStr,

this.reason,

});

}

```

**هندلر جدید `_handleRoutineReschedule` — در یک تراکنش واحد:**
1. رخداد امروز: `status = 'rescheduled'` (⚠️ مقدار جدید — بررسی کن که هیچ کوئری‌ای وضعیت‌ها را با فهرست بسته فیلتر نکند؛ خروجی `P0-7`)
2. رخداد مقصد را با `INSERT OR IGNORE` بساز: `status = 'pending'`, `scheduled_time` همان زمان اصلی
3. دلیل را در `skip_reasons` ثبت کن (T5)
4. `_notifySuccess` برای **هر دو** تاریخ — ⚠️ `invalidateDate` باید برای `fromDateStr` **و** `toDateStr` صدا زده شود، وگرنه تقویم فردا کهنه می‌ماند

**قیدها:**
- اگر رخداد فردا از قبل وجود دارد → دست نخورده بماند، `CompletionOutcome.success` با پیام «از قبل برای فردا برنامه‌ریزی شده بود»
- ⛔ برای روتین با `recurrenceRule` روزانه این گزینه اصلاً نمایش داده نشود (T1)
- `undoToken` برگردانده شود که هر دو تغییر را برگرداند

**متن دکمه اصلاح شود** به «به فردا موکول کن» و پیام موفقیت به «به فردای همین ساعت منتقل شد».

**رفع:**
- اگر `P0-3` جدول را پیدا نکرد، در `MigrationV56` بساز:

CREATE TABLE IF NOT EXISTS skip_reasons (

);

CREATE INDEX IF NOT EXISTS idx_skip_reasons_item ON skip_reasons(itemId, dateStr);

- `_handleRoutineSkip` **در همان تراکنش** هم در `routine_completions` بنویسد (سازگاری عقب‌رو) **و هم** یک ردیف در `skip_reasons`
- `_handleRoutineReschedule` هم با `reason: 'موکول شد به فردا'` بنویسد

⛔ ستون `reason` از `routine_completions` حذف **نشود** — داده‌های موجود باید بمانند.

## بخش ۴ — بازگردانی چنددامنه‌ای

### T7 — **B4: `undo()` فقط روتین را می‌شناسد** 🔴

```

final rows = await db.query('routine_completions', where: 'id = ?', whereArgs: [undoToken]);

...

return CompletionOutcome.failure('توکن لغو یافت نشد');

```

دوره، عبادت، دارو، گام هدف و **حتی حرکت** (که `undoToken` معتبر برمی‌گرداند) همگی شکست می‌خورند. دکمهٔ «بازگردانی» برای پنج دامنه از شش دامنه مرده است.

**رفع — توکن دامنه‌دار. ⛔ جدول جدید نساز.**

قالب توکن: `'<domain>:<recordId>'`

```

// تولید:

CompletionOutcome.success(undoToken: 'routine:$undoId')

CompletionOutcome.success(undoToken: 'movement:${[event.id](http://event.id)}')

CompletionOutcome.success(undoToken: 'course:${req.sessionId}')

CompletionOutcome.success(undoToken: 'worship:$logId')

CompletionOutcome.success(undoToken: 'medicine:$logId')

CompletionOutcome.success(undoToken: 'goalStep:${req.goalId}|${req.stepId}')

CompletionOutcome.success(undoToken: 'reschedule:$routineId|$from|$to')

```

`undo()` روی پیشوند `switch` کند:

| دامنه | عمل بازگردانی |
|---|---|
| `routine` | حذف از `routine_completions` + `status = 'pending'` |
| `movement` | `MovementRepository.instance.deleteEvent(id)` |
| `course` | `completionStatus = 'PENDING'`, `isCompleted = 0`, `completedAt = null` |
| `worship` | حذف ردیف از `worship_logs` |
| `medicine` | حذف ردیف از `medication_logs` |
| `goalStep` | `isCompleted = 0`, `completedAt = null` |
| `reschedule` | رخداد مقصد حذف، رخداد مبدأ → `pending`، ردیف `skip_reasons` حذف |

**سازگاری عقب‌رو اجباری:** اگر توکن `:` نداشت، رفتار فعلی (جست‌وجو در `routine_completions`) اعمال شود. توست‌های باز در لحظهٔ به‌روزرسانی نباید بشکنند.

پس از هر بازگردانی موفق: `DayAgendaService.instance.invalidateDate(...)` و رویداد `completionRecorded` با `'didWrite': true`.

⛔ هر شاخهٔ ناموفق باید پیام فارسی مشخص بدهد، نه «توکن لغو یافت نشد» عمومی.
